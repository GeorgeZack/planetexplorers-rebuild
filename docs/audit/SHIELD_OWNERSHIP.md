# Wood Shield ownership and PECS v15

October 6, 2026. This covers bounded ownership/persistence and headless hunt damage integration for the source starter Wood Shield34, described in [starter sword/shield readiness](STARTER_SWORD_SHIELD.md). The hunt controller accepts a qualified transient block request; normal shield UI use and visible blocking remain unavailable until the frontend and recovered presentation are integrated. This is not general armor support.

## One bag owner, two independent equipment references

The native primary equipment model already retains its exact item and durability in an inventory slot. The new `PeGame.shield_instance_id` follows that model: it selects one exact Wood Shield34 bag instance independently of `equipped_instance_id`. The bag remains the sole mutable owner; there is no second item/durability copy in saved state. A matching quickslot is another allowed reference. Worn clothes, deployed objects and primary equipment must not alias the selected shield identity; duplicate bag identities and malformed nonmatching quickslot references are rejected.

`pe_shield_equip` and `pe_shield_unequip` are atomic reference operations. They preserve inventory, instance allocation, durability and primary equipment, including when the bag is full. Swapping between two existing shield instances does not repair either. This is the existing native inventory/equipment representation, not a claim that the original equipment receiver's transfer/capacity behavior has been reproduced. Fresh sessions infer no equipped shield; receiving item34 in supplies does not equip it automatically. Ordinary item-use remains unavailable at this foundation stage, avoiding an invisible equipped shield.

`pe_shield_equipped` returns a validated borrowed bag slot. A depleted instance can remain selected, but `pe_shield_defense` and `pe_shield_protection` return0. Intact exact34 contributes source defence9 and protection attribute.22. The latter is not an unconditional damage reduction: a supported source damage path and transient block/action eligibility must be provided by the combat host.

`pe_shield_wear` accepts a validated slot or staged copy and subtracts source `max(0, calculated_damage*.1)`, clamped at0. It does not mutate the owning game when called on a transaction-local copy. The caller must commit that exact slot with the rest of a successful combat transaction, use calculated damage before remaining-HP clamping, apply wear only once per accepted hit, and bypass wear in Build. Invalid input is atomic; negative damage does not repair. This ownership module contains no saved or transient block flag and does not itself dispatch damage.

Ordinary bag removal clears a missing shield reference on the same shared cleanup path as primary/quickslot references. Cleanup does not erase an existing malformed item to make it appear valid. Source values come from `pe_starter_sword_shield_source.h`, generated by the audited exporter; no generated output was hand-edited.

## Four-byte save contract

**PECS v15 preserves the complete literal v14 payload and appends exactly one little-endian uint32 `shield_instance_id` (4 bytes).** Zero means no shield. A nonzero reference must resolve to exactly one valid item34 inventory instance, with finite current durability in `[0,4312]` and valid ownership. The existing bag record carries item ID and durability; neither is duplicated in the extension. There is no persisted blocking flag.

Versions1–14 infer no shield, even if a Wood Shield is in the bag or assigned to a quickslot. A literal v14 load retains outfit identities/wear and the shared allocator unchanged. The existing pre-v14 intact-outfit compatibility migration remains separate and unchanged. Current saves never repair a malformed shield reference, silently select a different shield, or recreate a missing instance. Failed loads preserve the entire destination, including its owned world; failed saves do not replace the checkpoint.

## Incoming hunt damage transaction

`PeHuntCombatPlayer` now accepts an optional borrowed `PeSlot *shield` and transient `bool shield_block`. The caller must resolve the selected bag instance through validated shield ownership; the controller checks exact item34, count1, nonzero identity and finite bounded durability. It receives **base defence** in `player.defense`, then adds the current staged clothing and shield attributes. Supplying an already summed equipment defence would count equipment twice. `NULL` preserves existing no-shield behavior, including when a stale block request is true.

`pe_hunt_combat_step` stages the shield bag slot alongside outfit wear, HP, stamina, quest credit, action clocks and contact deduplication. Every accepted real hare forearm contact uses current base + outfit + shield defence. An intact shield contributes9 passively; a qualified block additionally multiplies that source damage by `1-.22`. This exact hare damage path does not add a facing cone or a shield collider. Both clothing and shield wear use the calculated capsule damage before clamping to remaining HP, once per accepted hit. A piece breaking on an earlier hit loses its defence/protection before a later hit in the same tick. Depleted shield ownership remains valid and yields no attributes.

The controller suppresses a block request if the blade was active at tick entry, remains active after advancing, or has a pending split tick with a valid outgoing attack interval. This includes an ending attack whose clock was already advanced by the movement host; protection cannot appear halfway through that tick. A fresh eligible host snapshot may restore blocking on a later tick. The controller does not store a block latch, poll keys, qualify a shield pose, or introduce a second action clock.

Nothing commits until the complete hunt tick succeeds. A later invalid incoming contact leaves the original bag slot, clothing, HP, stamina, quest credit, clocks, deduplication and caller outputs unchanged. The pointer must refer to the authoritative selected bag slot for that transaction, rather than a separate persistent durability owner. Frontend modal/focus/death/load/unequip eligibility and Build wear bypass remain caller responsibilities; this six-hare Adventure controller is not a Build damage system.

### Headless incoming-contact evidence

The expanded `test_hunt_combat.c` passed optimized and strict ASan/UBSan runs with `ASAN_OPTIONS=detect_leaks=1:halt_on_error=1` and `UBSAN_OPTIONS=halt_on_error=1`. Both final builds and runs exited0, emitted no compiler warnings, and had **zero asset-dependent skips**. The final focused build/run sequence took80.35 seconds; it includes the split ending-tick regression. Evidence and tested source hashes are under ignored `rebuild/build/shield-hunt/{optimized.log,sanitize.log,verification.json}`. No full-suite result is inferred from this focused check.

The fixture acquires a real sensor target and advances the existing hare attack/skill clocks until recovered forearm and player defence capsules contact. It replays that checkpoint to compare passive shield9, blocked shield9 with.22 protection, depleted shield, absent shield, and additive clothing12 + shield9. It checks calculated overkill wear and verifies shield/clothing wear is applied once. Two actual posed actors are deliberately colocated with distinct entity identities to establish that first-hit shield breakage changes the second hit within one transaction. A malformed second actor guide record then proves full rollback after the first actor would already have staged damage and both wear updates. Additional cases cover malformed shield slots, incoming hits during active blade actions, naturally advanced ending ticks and preadvanced split ending ticks.

This is an arranged headless geometry fixture using real recovered poses. It does not establish visible shield/block layering, original blocking timing, normal keyboard eligibility, physical survival improvement, a completed four-hare hunt, or full source AI parity. No desktop input or new original-game observation was performed for this increment.
