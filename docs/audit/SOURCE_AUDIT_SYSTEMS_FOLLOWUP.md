# Source-first systems follow-up

October 6, 2026, US/Central. Baseline: `3791d89e763586a5cd3bc7684c6462592288572a`. This is a read-only source/C comparison outside combat and quest progression. It supplements [the recording review](SOURCE_CAPTURE_REVIEW.md), rather than claiming a new original or native playtest. Only this document was written; no game, recorder, desktop input or runtime test was launched.

The strongest next work is inventory capacity/transactions, camera obstruction behavior, construction history, and species-aware tree resources. Their rules are available locally. A user-operated half-hour recording can consolidate visual and usability observations, but none of these rules requires another original-game session to discover its constants.

## Confirmed differences and bounded implementation candidates

### 1. Inventory capacity is a gameplay difference, not merely missing pages

Original [PlayerPackageCmpt.cs](../../Assets/Scripts/PeEntity/Cmpt/PlayerPackageCmpt.cs#L11) sets `PkgCapacity=420` and passes it to `PlayerPackage` at line35. [PlayerPackage.cs](../../Assets/Scripts/ZhangShunBo/PlayerPackage.cs#L16) creates the regular package and, when requested, a separate mission package. [ItemPackage.cs](../../Assets/Scripts/Items/ItemPak/ItemPackage.cs#L500) allocates that capacity separately to Item, Equipment, Resource and Armor lists. This is evidence for the source allocation path, not a claim that every category in every loaded archive is full or uses all slots.

Native [pe_game.h](../../rebuild/src/pe_game.h#L11) defines **32 slots total**. [UI filtering](../../rebuild/src/pe_sandbox_ui_input.c#L91) counts occupied entries from that same array by tab and hides equipped instances; it does not create category capacity. Consequently, filling one category can prevent acquisition in another. Native capacity failures are deliberate, tested transactions; they are not evidence that the original has the same capacity boundary.

The source also exposes stack split through [UIItemPackageCtrl](../../Assets/Scripts/Chenzhi/NewUI/Scripts/PE_GameUI/GameWnd/UIItemPackageCtrl.cs#L600) and [ItemPackage.Split](../../Assets/Scripts/Items/ItemPak/ItemPackage.cs#L193), plus slot exchange/drop and sorting paths. Native [inventory dragging](../../rebuild/src/pe_sandbox_ui_input.c#L470) currently selects an item and assigns/exchanges **quickslots** on release; it does not rearrange inventory cells or split stacks. Native stack shortcuts intentionally use item IDs rather than durable equipment instance IDs. A source stack's identity must therefore not be copied into C without deciding how that interacts with existing shortcut semantics.

**Offline next increment:** export/guard the source category-capacity and slot classification contract, then implement category-aware storage and paging with an explicit migration. Keep durable item identities, worn/equipped ownership and atomic full-capacity rejection. Follow with split/reorder UI through the same owner. Source split code subtracts before its add call; inspect UI/preflight and failure semantics before copying that sequence. Native failure atomicity should remain an explicitly documented policy.

Do **not** simply change `PE_INVENTORY_SLOTS`: [pe_save.c](../../rebuild/src/pe_save.c#L149) uses it in the literal old inventory payload and again for v2 instance/wear records. A global constant change would reinterpret every historical save. Keep the old32-slot wire prefix fixed, append/version the expanded representation, and test category saturation, migration identity/quickslot preservation, full split rollback, save/reload order and corrupt category/count rejection. Existing [game inventory tests](../../rebuild/tests/test_game.c#L43), [UI tests](../../rebuild/tests/test_sandbox_ui.c), and historical save suites are the starting point. No screenshot is needed to determine420 or the old prefix size.

### 2. Camera activity-space and obstruction recovery are directly portable

The C camera already has source-verified scalar SmoothDamp and three input modes. Preserve those owners. The missing behavior is concrete: original [ThirdPersonFollow](../../Assets/PeCamera/Scripts/ScriptModifier/ThirdPersonFollow.cs#L152) starts a two-second lock after geometry clamp, calculates `clamp(ActivitySpace*.15,.15,1)`, applies the activity-dependent maximum and only resumes ordinary distance recovery under the source conditions at lines245–253. [PeCamera](../../Assets/PeCamera/Scripts/PeCamera.cs#L197) computes activity space through [Utils.EvaluateActivitySpaceSize](<../../Assets/Camera Forge/Scripts/Utilities/Utils.cs#L42>). [GeometryClamp](../../Assets/PeCamera/Scripts/ScriptModifier/GeometryClamp.cs#L58) adds near-plane visibility/sphere queries and communicates the clamp event.

Native [game_camera](../../rebuild/src/pe_sandbox_view.c#L264) still uses eye height1.58, an eye-plus-two-direction target, a0.5m rise and a0.1m-radius geometry sweep. [pe_sandbox_camera_step](../../rebuild/src/pe_sandbox_camera.c#L47) smooths desired zoom but has no activity-space input or clamp-lock owner. These are documented adapters, not a newly reproduced camera defect.

**Offline next increment:** a pure activity-space evaluator with supplied ray queries, followed by explicit clamp/recovery state and a separate near-plane geometry query. Read the serialized graph parameters/order already documented in [SANDBOX_CAMERA](SANDBOX_CAMERA.md); constructor defaults are not authoritative active values. Keep camera queries tree-excluding and distinct from player movement. Tests should cover open space, narrow corridor, partially visible obstacle, clamp plus wheel input, the two-second boundary, paused time, and one display update despite multiple simulation catch-up steps. Integrate the verified math before asking for a corridor/camera acceptance video. Exact visual framing still needs that final comparison; this would not by itself port the entire CameraForge graph.

### 3. Construction history exists in source and is absent from native input

Original [BSHistory](<../../Assets/Scripts/WuYiqiu/Building System/Scripts/Action/BSHistory.cs#L7>) retains five actions, clears redo on a new action, and walks separate undo/redo lists. [BuildingMan.Update](<../../Assets/Scripts/WuYiqiu/Building System/Scripts/BuildingMan.cs#L196>) routes input to it. [BSVoxelModify](<../../Assets/Scripts/WuYiqiu/Building System/Scripts/Action/BSVoxelModify.cs#L105>) performs inverse operations through `onModifyCheck` and `onAfterDo`; it is not a free copy of an earlier world. [PEBuildingMan](<../../Assets/Scripts/WuYiqiu/Building System/Scripts/PEBuildingMan.cs#L368>) supplies material checks/debits, with subtraction/refund handling later in the same file.

Native [pe_game.c](../../rebuild/src/pe_game.c#L610) stages construction placement/removal and material transactions directly, but its game/UI/host paths have no undo/redo owner. The existing [cost/refund functions](../../rebuild/src/pe_block.c#L79) already implement ceiling/floor division by4; replacing those formulas is unnecessary. Creation saving and selection deletion are separately labeled unavailable in [the UI](../../rebuild/src/pe_sandbox_ui.c#L589).

**Offline next increment:** a transient five-action cell journal for currently supported cube/ramp edits, preserving source check/after-callback meaning and one collision/render invalidation per committed operation. Qualify source history-clear and failed-undo behavior before choosing native lifecycle semantics; `BSHistory` itself ignores the boolean returned by `BSAction.Undo`, so a stronger native transactional policy must be labeled. Tests must include insufficient materials, full refund capacity, intervening occupied cells, sixth-action eviction, redo invalidation and load/world replacement. Do not add persistent history or claim creation-editor coverage from this bounded slice. [Existing block tests](../../rebuild/tests/test_block.c#L101) protect rounding independently of presentation.

### 4. Tree collision is recovered; tree resource identity/scale is still provisional

The C source explicitly states the remaining gap in [pe_game_cut_tree](../../rebuild/src/pe_game.c#L855): it subtracts player/tool cut damage, then gives the tree's stored Wood count on depletion. Generic initialization [creates twelve trees](../../rebuild/src/pe_game.c#L241) with eight stored Wood and HP255. This initialization evidence does not establish the location or species of every tree in an imported world.

Original [DigTerrainManager.Fell](../../Assets/Scripts/BuildNDig/DigTerrainManager.cs#L877) looks up `NaturalRes` using prototype index+1000 and subtracts `damage*duration/(heightScale*widthScale)`. `GetTreeResouce` at line902 uses either fixed count or `selfCount*widthScale²*heightScale*(1+bonus)`, a minimum of1, integer primary-drop trials and separate extra/special branches. This file is UTF-16; decode it before tooling/source guards. The current [content exporter](../../rebuild/tools/export_content.py#L219) deliberately limits its terrain-resource extraction to IDs≤255 and primary drop lists. It therefore does not already supply the tree1000+ table, and its preserved production strings are not implemented extra-drop behavior.

**Offline next increment:** export tree resource rows and their exact prototype association, then implement a pure scaled health/yield transaction with deterministic injected draws and source-derived threshold tests. Preserve existing [tree collision provenance](../../rebuild/tools/export_tree_collision.py#L15); add identity/scale to world records only with a supported migration and matching render/query dimensions. Do not infer species from the currently displayed tree11 mesh, assign arbitrary source scales, or present a prototype table as recovery of Adventure vegetation placement. The species/instance data gate remains distinct from the mathematical port. No new felling animation capture is required to implement resource rules; the shared [tool event owner](../../rebuild/src/pe_sandbox_actions.c#L97) already calls the transaction.

## Foundations to preserve, rather than rebuild again

Recovered UI atlas/layouts, movable windows and numbered responses already have source/physical evidence in [TRAINING_UI](TRAINING_UI.md), [NUMBERED_CONVERSATIONS](NUMBERED_CONVERSATIONS.md) and [PLAYTEST](../PLAYTEST.md). Their input routes must keep modal ownership through closing/release frames. New split/undo controls must not leak a number, mouse press or held button into tools or construction. The intentional native medicine final-acknowledgment policy is not a defect to rediscover from footage.

PECSv16 already persists raw comfort after the literal earlier payload, validates staged state, migrates old outfit ownership and commits successful loads by move. [Save writing](../../rebuild/src/pe_save.c#L348) uses a temporary file, flush/fsync and rename; [loading](../../rebuild/src/pe_save.c#L367) checks version, size/checksum and state before replacing the game. This audit found no new save corruption reproduction. Inventory/tree extensions should preserve that architecture and strengthen their own migration fixtures rather than weakening historical assertions. Original Unity archive compatibility remains a separate feature, not something a native save test implies.

## What a half-hour user recording would add now

The existing [recording review](SOURCE_CAPTURE_REVIEW.md#actual-recording-capabilities-and-limits) remains accurate: the pose observer stops at120 seconds,3600 frames or256MiB; its1800-second wait is **not** a half-hour capture mode. The hunt and town-defense observers have different64/16MiB limits and still120-second active bounds ([hunt probe](../../rebuild/tools/ReferenceHuntCombatProbe.cs#L36), [town probe](../../rebuild/tools/ReferenceTownDefenseProbe.cs#L20)). Increasing all limits would not create synchronized input/transaction telemetry or eliminate observer cost.

Additional local capability checks in this audit found `/usr/bin/obs`, `/usr/bin/ffmpeg` and `/usr/bin/gpu-screen-recorder`. The latter's installed `-h` output and `/usr/share/man/man1/gpu-screen-recorder.1.gz` document Wayland portal capture, frame-rate selection, GPU/CPU encoding, CBR bitrate, a first-frame timestamp sidecar and SIGINT stop-and-save. This establishes available tooling, **not** verified capture-source selection, encoder support/performance on this GPU, or successful recording. The operator should use one recording route, test a short file first, and leave the user as sole game-input operator. [reference_input.py](../../rebuild/tools/reference_input.py#L13) is unsuitable as a passive companion: its commands focus the game and can inject input; it is a bounded still/input tool, not a recorder.

For this session, ordinary game-window/region video with an elapsed-time note is sufficient. No microphone or system-wide audio is needed; capture only the intended game area so unrelated windows/notifications do not become reference material. A proposed720p/30fps H.264 recording at6Mbit/s has a nominal30-minute payload of1.35GB before container/audio overhead. That is a storage estimate, not a measured output or hard size cap. Quality-based encoding varies with content. Validate output/free space and a30-second playback before committing a half-hour; compare responsiveness with recording enabled, rather than attributing any slowdown to gameplay logic.

Native `PE_SANDBOX_PROFILE=1` reports per-stage totals/maxima at120 frames and exit; it is not a continuous frame-time trace or original-client telemetry ([implementation](../../rebuild/src/pe_sandbox_view.c#L36)). `PE_SANDBOX_COMBAT_TRACE=1` is bounded to4096 changed-hit/kill records, not a general input/UI log. Neither should be advertised as a synchronized half-hour reference observer. Retain start/end Player.log, process outcome, renderer/profile identity, and starting/new save hashes where applicable. The existing original graphics workarounds have bounded successes and failures in [REFERENCE_RUNTIME](../REFERENCE_RUNTIME.md#october6-zink-hardware-accelerated-comparison); do not promise30-minute stability or change global graphics settings for this audit.

The footage can replace repeated **broad observation** sessions and identify the next user-visible mismatch. It cannot prove exact hidden clocks, source slot IDs, randomized yield distributions, collision masks, all save migrations or composed humanoid phase coverage. Follow up offline with the matching source/data and saved state; request a later short original capture only for a named unresolved engine question. Native acceptance remains separate from observing the original.

## Verification and immediate order

This document's findings come from current source/runtime reads, local recorder help/manual reads and existing evidence, not newly executed game tests. Recommended order: guard inventory allocation/migration design; port camera activity/recovery math; add bounded construction history; qualify tree prototype/scale data before enabling its scaled yield. UI readability and the completed gameplay increments can share one user-led recording/acceptance session. These independent systems tasks can proceed while the animation/combat work uses its existing qualified captures.
