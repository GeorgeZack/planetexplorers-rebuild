## 1. P0: low-health recovery is an extractable missing survival rule

**Source.** `PlayerProtoDb` loads `initprop` and its `InitBuffList` ([PeEntityCreator.cs:749](../../Assets/PeWorld/PeEntityCreator.cs#L749)); the entity mounts those initial buffs ([PESkEntity.cs:258](../../Assets/Scripts/PeEntity/Cmpt/PESkEntity.cs#L258)). Player row1 includes buff30200046. Its `skBuff` row has interval1 and this exact condition/effect: `InCoolingForGettingHurt(4)` and `Hp/HpMax < .33`, then `Hp += HpMax*.01`. The damage notification records the hurt timestamp; the cooldown comparison is **greater than or equal to** last hurt plus4 ([SkExpFuncSet.cs:89](../../Assets/Scripts/SkillSystem/SkExpFuncSet.cs#L89), [line110](../../Assets/Scripts/SkillSystem/SkExpFuncSet.cs#L110)). Buff evaluation is an immediate initial execution, followed by **strict** `elapsed > n*interval`, at most one further interval evaluation per update ([SkBuffs.cs:159](../../Assets/Scripts/SkillSystem/SkBuffs.cs#L159)). It is not an unconditional continuous heal rate.

**C status.** [pe_game.c:375](../../rebuild/src/pe_game.c#L375) handles Juice916, Med Pack925 and stamina; it has no corresponding passive HP buff/hurt-age owner. Hunger/Comfort/Oxygen are not modeled by the present `PeGame`, and Character displays placeholders. Source `initprop1` also specifies Hunger300/500, Comfort500/500 and Oxygen500/500; buffs30200049/50 update comfort/hunger every5 seconds, while30200051 uses its own oxygen rule. Those rows can be exported now; no visual sampling is needed to discover them.

**Minimum next port/tests.** Export a guarded30200046 contract first, then add one authoritative scaled-game clock and hurt timestamp updated by every supported damage commit. Test 3.999/4-second admission, 164/500→169/500 versus165/500 not healing, one pulse after a large update, death, pause, repeated hits, healing-item interaction and save/load policy. Preserve the source threshold overshoot rather than clamping to165. Determine initial/load buff timing from the existing initialization/serialization path before choosing a compatibility adapter. Do not add hunger depletion alone before food, consequences and saved state are coherent. This is a source-derived correction, not difficulty tuning or evidence that the four-hare fight becomes survivable.

**Minimum next port/tests.** Introduce a runtime entity registry with explicit durable/transient identity domains before adding general NPC/monster/shop objects. Test ID exhaustion, stale references, repeated death notifications, cross-owner alias rejection, old-version defaults and failed-load atomicity. Extend PECS only for the chosen native state contract; source serializer omission does not prove that wave progress can be reconstructed from a single saved count. Existing archives can answer many reference-binding questions offline; a nonzero-defense-count reload remains a focused unresolved observation.

## Recommended next work and a bounded play session

The smallest source-backed implementation candidate is passive low-health recovery, after its clock/load contract is resolved. In parallel, a quest dependency/role export and defense spawn planner can progress headlessly. Selling/buyback and repair quotes provide useful economy work with exact source inputs. General NPC combat and three-species defense are larger integrations; procedural world generation is a separate program of work.

A30-minute session should answer a specific remaining question, not discover database content by trial and error: for example, original low-HP recovery after a timestamped last hit; one vendor sale/buyback of a worn instance; or defense partial-count save/reload. Native exploration/crafting/UI checks can use existing supported systems, but “30 minutes played” would not certify defense, survival, procedural world or later-quest parity. Preserve existing earned saves and use separate checkpoints for observations. This audit does not itself authorize or perform those desktop actions.
