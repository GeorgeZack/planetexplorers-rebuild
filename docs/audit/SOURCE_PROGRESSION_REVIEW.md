## 4. Add vendor wallets, exact-instance selling and buyback

**Priority: high independent town feature; source-only transaction tests first.** Current [pe_town_shop_buy](../../rebuild/src/pe_town_interaction.c#L42) owns player debit and stock but no vendor wallet or buyback. [UIShopWnd.Sell](../../Assets/Scripts/Chenzhi/NewUI/Scripts/PE_GameUI/NGUIScripts/UIShopWnd.cs#L187) checks/debits the NPC purse, moves the same object for unstackable items, creates a separate sold stack otherwise, and credits the player. [GetSellPrice](../../Assets/Scripts/Items/ItemObj.cs#L412) truncates `baseCurrency*(.8*condition+.2)` per item before quantity multiplication. The source binds buyback lists to NPC IDs through `StroyManager.m_SellInfo` and copies them when closing the shop ([UIShopWnd.cs:846](../../Assets/Scripts/Chenzhi/NewUI/Scripts/PE_GameUI/NGUIScripts/UIShopWnd.cs#L846)).

**Newly identified asymmetry:** [StroyManager.BuyItem](../../Assets/Scripts/Mission/StroyManager.cs#L279) charges the player `GetSellPrice()` for buyback, while [UIShopWnd.Buy](../../Assets/Scripts/Chenzhi/NewUI/Scripts/PE_GameUI/NGUIScripts/UIShopWnd.cs#L518) calculates the NPC credit from `prototype.currency`. A worn-item round trip need not conserve combined currency. Implement/document this observed-in-code behavior, or label any intentional correction; do not silently unify both prices. This review has not established a serialized buyback list—repository searches show the in-memory dictionary and UI lifecycle, not a persistence owner. Decide the native save adapter only after tracing the archive path.

**Smallest implementation/test:** exported supported-vendor purse parameters and exact item currency/condition rules; staged sell/buyback against one authoritative inventory-instance owner. Verify stack split, insufficient purse, full-bag buyback, integer rounding, different NPC lists, same worn instance returned, equipped/deployed alias rejection, and the unequal source debit/credit. Decode existing archived NPC purses before adding a new RNG adapter. This is not dependent on new animation or a complete general NPC AI.

**Remaining gameplay:** one final sale/buyback UI acceptance check, if wanted; no exploratory vendor playthrough is needed for the arithmetic. Existing earned inventory must not be used as a disposable test fixture.

## 5. Ship repair quotes before connecting a repair machine

**Priority: medium independent economy foundation.** Exact source repairs for the supported worn equipment are already data: Sword1/Shield34 Wood279×4 base, clothes95/131 Cloth1006×2,192 Cloth1006×1. [Repair.GetRequirements](../../Assets/Scripts/Items/ItemObj.cs#L1280) scales each material by missing condition with ceiling and an epsilon guard. The active [repair UI](../../Assets/Scripts/Chenzhi/NewUI/Scripts/PE_GameUI/NGUIScripts/UIRepairWnd.cs#L365) separately computes per-material ceiling with multiplier1; keep these branches distinct at tiny damage rather than assuming the helper is the UI itself.

Current C has durable worn instances but no repair owner. A pure quote API can be implemented now with exact supported component metadata and tests for intact, tiny damage, fractional and broken equipment, invalid durability, per-material rounding, and unchanged identity. The subsequent transaction must reserve the exact item, debit materials atomically and complete the same instance.

**Do not make repair instantaneous:** [CSRepair.CountFinalTime](../../Assets/Scripts/WuYiqiu/Colony%20System/Scripts/Entities/CSRepair.cs#L127) uses base time, `pow(.82,workerCount)` and worker parameters; `RecountCounter` preserves progress fraction when conditions change. `StartCounter`/`OnRepairItemEnd` own the timed machine flow. Supporting a particular town machine requires its source prefab/state and working counter conditions, not a generic player inventory button. Machine transforms/state can be inspected from existing building/archive inputs. Final UI/timer presentation needs a bounded native acceptance check; exact material costs need no live capture.
